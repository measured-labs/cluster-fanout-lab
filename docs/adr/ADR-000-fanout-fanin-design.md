# ADR-000: 파일 · DB 저장소 위의 Fan-out/Fan-in 설계

- 상태: 예정 — 설계 문서만 있고 코드는 아직 없다. 실행 결과 기록도 없다.
- 날짜: 2026-11-18(설계 문서를 이 ADR로 정리한 날. 원래 설계는 첫 커밋 `1a61038`에 있다)
- 성격: 설계 · 범위 정리. 원문은 `docs/archive/`로 옮겼다. 원문 내용은 그대로 두고 머리말 3곳 · 예상 표시 3곳 · 낱말 1곳만 바꿨다(§7 대응표).

## 1. 이 랩이 묻는 것

데이터를 N개 파티션으로 나눠 병렬로 처리하고(Fan-out) 결과를 합칠 때(Fan-in), 스레드 수 · 파티션 수 · 저장소(파일, DB)에 따라 전체 시간과 합치는 비용이 어떻게 달라지는가. 그리고 저장소를 파일에서 DB로 바꿔도 합치는 코드(`WordCountAggregator`)를 그대로 쓸 수 있는가.

주제는 큰 텍스트 파일의 단어 빈도 집계다. 한 대의 PC, 한 JVM 안에서 돈다.

## 2. 설계

```
[원본 txt] ─분할─▶ 파티션 N개 (파일 또는 H2 테이블)
                      │
        Coordinator가 가상 스레드 Worker N개 생성 (Fan-out)
                      │
   Worker마다 자기 파티션에서 Map<String, Long> 집계 (공유 상태 없음)
                      │
        WordCountAggregator가 Map을 합산 (Fan-in, 파일 · DB 공용)
                      │
        AnalysisResult + PerformanceResult(전체 시간 · Worker별 시간 · 합산 시간 · 속도 향상 비율)
```

| 단계 | 파일 방식(원문 Phase 1) | DB 방식(원문 Phase 2) |
|------|------------------------|----------------------|
| 분할 | `FilePartitioner` — 줄 단위 라운드 로빈으로 `data/partitions/partition_N.txt` | `DataDistributor` — 줄 단위 라운드 로빈으로 `text_partition_N` 테이블, 1,000행 배치 INSERT |
| Worker | `FileWordCounter` — `BufferedReader`로 읽고 소문자 · 특수문자 제거 · 공백 토큰화 | `DbWordCounter` — `SELECT content`로 읽고 같은 토큰화 |
| Coordinator | `FileClusterCoordinator` — `newVirtualThreadPerTaskExecutor()`, 모든 Future를 기다린 뒤 합산 | `DbClusterCoordinator` — 같은 구조 |
| 합산 | `WordCountAggregator` (공용) | 같은 클래스 |
| 비교 대상 | 단일 스레드 모드(같은 Aggregator, Worker를 한 스레드에서 차례로) | 단일 테이블 · 단일 스레드 모드 |

- 기술 스택(설계안): Java 21 가상 스레드, Spring Boot 3.5.8, H2 내장 DB, Gradle, Spring Web MVC REST API.
- 샤딩은 한 H2 인스턴스 안의 테이블 여러 개로 흉내 낸다. 네트워크 지연과 노드 장애는 다루지 않는다(원문 Phase 2 §3.1의 한계).
- API · 패키지 구조 · 테이블 스키마 · 응답 형식은 원문에 그대로 있다(§7).

| 넣는 것 | 넣지 않는 것 |
|---------|-------------|
| 파일 방식, DB 방식 두 저장소 | 여러 대의 서버, 실제 분산 DB |

## 4. 선택지

원문에서 고르지 않았거나 서로 다르게 적힌 것이다. 코드를 만들기 전에 정한다.

| 항목 | 선택지 | 원문 상태 |
|------|--------|----------|
| DB Worker의 집계 위치 | A. SQL 집계(DB 엔진이 집계) · B. 애플리케이션 집계(Java에서 토큰화 · 집계) | 원문 Phase 2 §4.2는 B를 기본으로 둔다. 그런데 A의 예시 SQL도 `SELECT content`뿐이라 실제로는 B와 같고, 설계 문서 §7 표는 Worker 처리를 "SQL GROUP BY 집계"로 적었다. 아직 정하지 않았다 |
| 스레드 종류 | 가상 스레드 · 플랫폼 스레드 | 가상 스레드로 정했다. 둘을 비교하는 실험은 확장안(원문 설계 §9)으로 남겼다 |
| 합산 방식 | Coordinator가 모든 Worker를 기다린 뒤 한 번에 합산(동기) · `CompletableFuture`로 끝나는 대로 합산 · 계층 트리 합산 | 동기 방식으로 정했다. 나머지 둘은 확장안 |
| 진행률 보기 | 없음 · WebSocket 실시간 진행률 | 확장안 |
| DB 인스턴스 | H2 하나에 테이블 여러 개 · H2 인스턴스 여러 개 | 하나로 정했다. 여러 개는 확장안 |

## 5. 예상과 확인할 것

아래는 원문(설계 §6.3, Phase 2 §6.2)의 **예상(실측 아님)** 이다. 결과처럼 읽지 않는다.

- 스레드 수가 CPU 코어 수를 초과하면 성능 향상이 둔화된다(Amdahl의 법칙).
- 합산 시간은 파티션 수에 따라 늘어난다.
- 데이터가 작으면 병렬 처리가 단일 스레드보다 느릴 수 있다.
- DB 방식은 INSERT 인덱스 갱신 · SQL 파싱 · 커넥션 관리 비용 때문에 느릴 수 있고, 버퍼 캐시 · 커넥션 풀 때문에 빠를 수도 있다.

원문 API 응답 예시의 수치(`totalTimeMs` 245, `speedupRatio` 3.42 등)도 **예상(실측 아님)** 이다. 코드가 없어서 잰 적이 없다.

반드시 같아야 하는 것(원문 Phase 2 §6.3): 파일 방식과 DB 방식의 최종 단어 빈도, Aggregator 코드, Fan-out/Fan-in 구조.
